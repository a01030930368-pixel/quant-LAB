# 제1장. 시스템의 목적

### 1.1 최종 목표

QUANT LAB은 실전 수익 가능성이 있는 퀀트 전략을 자율적으로 발굴·검증·개선하는 AI 기반 연구 시스템이다.

시스템은 다음 여섯 가지 기능을 중심으로 설계한다.

1. AI 기반 투자 가설 생성
2. 전략 구현 및 실험 실행
3. 재현 가능한 백테스팅
4. 독립적인 통계·위험 검증
5. 전략 채택·보류·탈락 판정
6. 연구 결과 축적 및 후속 연구

연구 전략의 개수나 소프트웨어 기능의 규모는 최종 성과지표가 아니다.

최우선 목표는 실제 시장에서 지속 가능한 투자 우위를 발견할 가능성을 높이는 것이다.

### 1.2 설계 철학

시스템은 다음 원칙을 따른다.

* 초기에는 모듈형 모놀리식 아키텍처를 사용한다.
* 정확성, 재현성, 데이터 품질을 개발 속도보다 우선한다.
* 연구 AI와 전략 검증 시스템의 책임을 분리한다.
* 정식 평가 기준은 실험 결과를 확인하기 전에 고정한다.
* AI의 자율성은 유지하되 핵심 검증 규칙의 우회는 허용하지 않는다.
* 외부 유료 서비스와 실거래 기능은 기본적으로 비활성화한다.
* 기능 확장은 측정 가능한 필요가 발생했을 때 수행한다.

# 제2장. 기술 스택

### 2.1 기본 개발 환경

초기 기술 스택은 다음과 같이 지정한다.

언어

* Python 3.12 이상에서 검증된 안정적인 버전

데이터 처리

* NumPy
* Pandas
* Parquet 및 PyArrow

통계 분석

* SciPy
* Statsmodels

백테스팅

* 초기에는 검증 가능한 오픈소스 엔진을 평가하여 채택하거나, 필요한 최소 기능을 직접 구현한다.
* 단, 직접 구현한 엔진은 기준 사례를 통한 독립적인 정확성 테스트를 통과해야 한다.

실험 기록

* SQLite
* 파일 기반 실험 아티팩트
* JSON 형식의 구조화된 설정 및 결과

테스트

* pytest

환경 및 패키지 관리

* Git
* uv 또는 동등한 Python 의존성 관리 도구
* 환경변수 기반 인증정보 관리

인터페이스

* 초기에는 CLI를 기본으로 사용한다.
* 대시보드는 필수 기능이 검증된 이후 도입한다.

### 2.2 기술 선택 원칙

위 기술 스택은 초기 기준안이다.

Claude는 호환성, 유지보수성 또는 실제 개발상의 이점이 입증되면 대체 기술을 제안하고 채택할 수 있다.

단, 기술 변경의 이유와 영향을 기록해야 한다.

불필요한 마이크로서비스, 분산 데이터베이스, 메시지 브로커, 복잡한 프런트엔드 프레임워크는 초기 단계에 도입하지 않는다.

# 제3장. 논리적 시스템 구조

### 3.1 핵심 구성 요소

시스템은 다음 여섯 개의 논리적 모듈로 구성한다.

#### A. RESEARCH ORCHESTRATOR

AI 연구 활동을 관리하는 중앙 조정 계층이다.

주요 책임:

* 연구 가설 생성 및 등록
* 연구 우선순위 결정
* 실험 계획 작성
* 실험 실행 요청
* 결과 분석
* 후속 연구 결정
* 연구 중단 및 재개

연구 오케스트레이터는 전략을 자유롭게 생성할 수 있지만 검증 판정의 원본 기록을 임의로 변경할 수 없다.

#### B. DATA ENGINE

금융 데이터를 수집·검증·보관한다.

주요 책임:

* 데이터 공급자 연결
* 가격 및 거래량 데이터 수집
* 데이터 품질 검사
* 시간 및 거래일 정렬
* 기업행동 처리
* 데이터 버전 관리
* 백테스트에 적합한 데이터 제공

데이터 출처와 사용 시점을 확인할 수 있어야 한다.

초기 개발은 합법적으로 접근 가능한 하나의 자산군과 신뢰 가능한 데이터 공급자부터 시작한다.

#### C. STRATEGY ENGINE

연구 가설을 실행 가능한 매매 전략으로 변환한다.

주요 책임:

* 신호 생성
* 진입 및 청산 규칙
* 포지션 크기 결정
* 전략 파라미터 관리
* 전략 코드 버전 관리

전략은 공통 인터페이스를 사용하여 백테스트 엔진과 연결한다.

전략 코드가 실행 결과나 검증 기준을 직접 조작할 수 없도록 책임을 구분한다.

#### D. BACKTEST ENGINE

과거 시장 환경에서 전략의 거래 과정을 재현한다.

주요 책임:

* 시간 순서 기반 데이터 처리
* 신호 및 주문 처리
* 체결 시뮬레이션
* 거래비용 반영
* 현금 및 포지션 회계
* 포트폴리오 가치 계산
* 거래 기록 및 성과 결과 생성

백테스팅 엔진은 AI가 제출한 전략을 실행하되 전략의 수익성을 높이기 위한 임의의 체결 가정을 적용하지 않는다.

#### E. VALIDATION ENGINE

전략의 신뢰성과 실전 적용 가능성을 평가하는 독립 검증 계층이다.

주요 책임:

* 데이터 및 코드 무결성 검사
* 표본 외 검증
* 위험조정 성과 분석
* 과최적화 및 다중검정 평가
* 거래비용 민감도 분석
* 강건성 검증
* PASS / HOLD / FAIL / INVALID 판정

검증 기준은 실행 전에 고정된 평가 설정을 통해 적용한다.

정식 검증 결과를 확인한 후 동일 실험의 통과 기준을 완화하는 행위를 금지한다.

#### F. RESEARCH REGISTRY

모든 연구 결과와 실험 이력을 관리하는 저장 계층이다.

주요 책임:

* 연구 가설 저장
* 전략 및 데이터 버전 기록
* 실험 설정 저장
* 실험 결과 저장
* 검증 판정 저장
* 실패 원인 기록
* 연구 상태 추적

원본 실험 기록은 원칙적으로 변경 불가능한 이력으로 보존한다.

잘못된 실험은 삭제하거나 덮어쓰는 대신 INVALID 판정과 수정된 새 실험을 연결한다.

# 제4장. 모듈 간 데이터 흐름

### 4.1 연구 실행 흐름

기본 연구 흐름은 다음과 같다.

RESEARCH ORCHESTRATOR
↓
연구 가설 및 실험 계획 생성
↓
DATA ENGINE
↓
STRATEGY ENGINE
↓
BACKTEST ENGINE
↓
VALIDATION ENGINE
↓
RESEARCH REGISTRY
↓
연구 결과 분석 및 후속 연구 결정
↓
RESEARCH ORCHESTRATOR

모든 실험은 고유 ID와 버전을 가진다.

### 4.2 검증 독립성

AI 연구원은 전략 코드와 탐색적 실험 설정을 수정할 수 있다.

그러나 다음 요소는 일반적인 전략 실행 과정에서 수정할 수 없어야 한다.

* 이미 확정된 정식 검증 설정
* 원본 실험 결과
* 원본 데이터 버전 식별자
* 보류 데이터 접근 정책
* 검증 엔진의 필수 통과 조건
* 실거래 권한 정책

초기 구현에서는 별도 보안 인프라 대신 명확한 모듈 경계, 제한된 실행 인터페이스, 버전 관리, 접근 제어 및 자동 테스트를 사용한다.

단, 동일한 운영체제 계정과 파일 수정 권한을 가진 AI가 코드 저장소 전체를 변경할 수 있다면 이러한 분리는 완전한 보안 경계가 아니다.

향후 무인 자율 연구로 확대할 때에는 검증 설정과 보류 데이터에 대한 운영체제 수준의 접근 제한 또는 독립 실행 환경을 도입해야 한다.

# 제6장. AI 자율 연구 시스템

### 6.1 자율 운영 범위

Claude 또는 연결된 AI 실행 계층은 승인된 환경에서 다음 작업을 독립적으로 수행한다.

1. 연구할 전략 가설 선택
2. 전략 코드 작성
3. 탐색적 백테스트 실행
4. 결과 분석
5. 필요 시 전략 수정
6. 정식 검증 요청
7. 검증 결과에 따른 연구 상태 변경
8. 다음 연구 방향 선택

연구 자율성은 연구 프로토콜의 준수를 전제로 한다.

### 6.2 자율 연구 루프

AI의 연구 루프는 다음과 같다.

```
START
  ↓
연구 목표 및 자원 확인
  ↓
가설 선택 또는 생성
  ↓
전략 구현
  ↓
탐색적 실험
  ↓
정식 검증
  ↓
판정
  ├── PASS → 후속 검증 단계
  ├── HOLD → 추가 증거 확보
  ├── FAIL → 실패 기록 후 다음 가설
  └── INVALID → 오류 수정 및 재검증
  ↓
연구 결과 저장
  ↓
예산·안전·중단 조건 확인
  ↓
NEXT RESEARCH
```

### 6.3 자율 실행의 현실적 제약

Claude Projects에 문서를 등록하는 것만으로 지속 실행형 연구 시스템이 완성되는 것은 아니다.

연구 시스템은 다음 기능을 별도로 갖춰야 한다.

* 프로그램 실행 환경
* 데이터 접근 수단
* 작업 실행 및 상태 관리
* 실험 결과 저장
* 실패 시 복구
* 자원 사용 제한
* 필요 시 AI 모델 호출 인터페이스

초기에는 사용자가 실행하는 단일 연구 작업부터 구현한다.

이후 안정성이 검증되면 예약 실행 또는 장시간 자율 연구를 도입한다.

AI API의 이용 비용과 호출 횟수는 사전에 승인된 한도를 준수한다.

# 제7장. 데이터 및 실험 관리

### 7.1 데이터 관리

원본 데이터는 가능한 한 수정 없이 보존한다.

정제 데이터는 원본의 식별자, 처리 코드 및 처리 설정과 연결한다.

동일 실험을 재현할 수 있도록 사용 데이터의 버전이나 해시를 기록한다.

### 7.2 실험 관리

각 실험은 다음 정보를 저장한다.

* experiment_id
* strategy_id
* strategy_version
* dataset_version
* configuration_version
* validation_policy_version
* code_commit
* random_seed
* execution_timestamp
* metrics
* verdict
* failure_reason

정식 검증 결과는 동일한 실험 ID로 덮어쓰지 않는다.

### 7.3 데이터베이스

초기에는 SQLite를 사용한다.

대규모 시장 데이터와 시계열 결과는 Parquet 파일로 관리하고 SQLite에는 해당 파일의 식별자와 메타데이터를 저장할 수 있다.

실험 규모가 실제로 증가하여 병목이 확인되기 전까지 별도의 데이터베이스 서버를 도입하지 않는다.

# 제8장. 시스템 정확성 테스트

### 8.1 필수 테스트

시스템은 다음 테스트를 제공해야 한다.

회계 테스트

* 매수·매도 후 현금 및 포지션 계산
* 수수료 및 세금 반영
* 손익과 포트폴리오 가치의 일치

시점 테스트

* 미래 데이터 참조 차단
* 신호 생성 시점과 주문 시점 구분
* 데이터 공시 시점 준수

거래 테스트

* 거래 불가능한 종목 처리
* 주문 수량 및 현금 제약
* 미체결 및 거래 중단 상황

검증 테스트

* 사전 고정된 검증 설정 준수
* 표본 외 데이터 접근 제한
* 검증 기준 미달 시 FAIL 처리
* 무효 데이터 사용 시 INVALID 처리

재현성 테스트

* 동일 입력으로 동일 결과 재생성
* 실험 결과 및 설정 복원

### 8.2 테스트 통과 원칙

핵심 회계 및 시간 순서 테스트가 실패한 상태에서는 전략의 성과를 정식 검증 결과로 인정하지 않는다.

백테스트 결과가 우수하더라도 시스템 정확성이 증명되지 않았다면 연구 성과로 채택할 수 없다.

# 제9장. 초기 개발 범위

### 9.1 최소 실행 버전 — MVP

첫 번째 목표는 하나의 전략을 처음부터 끝까지 올바르게 검증하는 것이다.

MVP 필수 조건:

1. 하나의 자산군 지원
2. 하나의 신뢰 가능한 데이터 공급자
3. 하나의 기준 전략 및 벤치마크
4. 기본 백테스팅
5. 현실적인 기본 거래비용
6. 시계열 표본 외 검증
7. 필수 성과 및 위험지표 계산
8. PASS / HOLD / FAIL / INVALID 자동 판정
9. 실험 결과 저장 및 재현
10. 핵심 단위·통합 테스트

초기 대상 시장은 데이터 품질과 확보 비용을 비교하여 결정한다.

기존 사용자 프로젝트에 한국 주식 데이터와 검증된 코드가 있다면 재사용 가능성을 평가할 수 있지만, 기존 자동매매 프로젝트와 시스템을 반드시 결합할 필요는 없다.

### 9.2 MVP 성공 기준

MVP는 수익성 있는 전략을 발견해야만 성공하는 것이 아니다.

다음 조건을 만족하면 기술적으로 성공한 것으로 간주한다.

* 정상적인 전략을 실행할 수 있다.
* 거래비용과 회계 계산이 정확하다.
* 데이터 누출을 방지한다.
* 독립 검증을 실행한다.
* 검증에 실패한 전략을 올바르게 탈락시킨다.
* 동일 실험을 재현할 수 있다.
* 사용자에게 결과와 근거를 보고한다.

MVP의 정확성이 확인되기 전에는 무작정 연구량을 확대하지 않는다.

# 제10장. 확장 정책

### 10.1 확장 우선순위

MVP 이후 확장은 다음 순서를 기본으로 한다.

1차 — 연구 품질 향상

데이터 품질 개선, 검증 방법 보강, 다양한 전략 유형 지원.

2차 — AI 연구 자동화

가설 생성, 실험 계획, 실행 및 후속 연구의 자율화.

3차 — 연구 범위 확대

추가 시장, 자산군, 전략 계열 지원.

4차 — 운영 효율화

병렬 실행, 실행 시간 최적화, 장기 작업 관리.

5차 — 사용자 인터페이스

연구 현황과 전략 결과를 시각화하는 대시보드.

이 순서는 실제 병목과 필요에 따라 조정할 수 있다.

### 10.2 과도한 개발 방지

다음 사항은 검증된 필요가 없으면 구현하지 않는다.

* 복잡한 멀티에이전트 조직
* 클라우드 분산 클러스터
* 대규모 실시간 데이터 파이프라인
* 고빈도 매매 인프라
* 복잡한 웹 서비스
* 모든 자산군의 동시 지원
* 불필요한 머신러닝 모델
* 실거래 주문 시스템

AI는 새로운 기능을 구현하기 전에 그 기능이 연구 품질, 연구 속도 또는 실제 수익 기회 검증에 어떤 도움이 되는지 확인해야 한다.

# 제11장. 개발 주도권

### 11.1 AI 개발 책임

본 아키텍처 확정 이후 Claude는 시스템의 세부 설계 및 개발을 주도한다.

Claude는 다음 업무를 수행한다.

* 개발 작업 분해
* 구체적인 구현 순서 결정
* 코드 작성과 테스트
* 의존성 관리
* 오류 분석과 수정
* 실험 기능 구현
* 연구 자동화의 점진적 확대
* 개발 기록 및 사용자 보고

모든 상세 설계 결정을 사용자에게 승인받을 필요는 없다.

다만 최상위 헌장의 수정, 검증 정책의 본질적인 완화, 유료 자원 사용, 실거래 권한 및 고위험 외부 작업은 승인을 받아야 한다.

### 11.2 사용자 역할

사용자는 연구소의 최종 감독자다.

주요 역할은 다음과 같다.

* 최종 연구 목표 설정
* 예산 및 인프라 승인
* 주요 운영 정책 승인
* 실거래 여부 결정
* 연구 성과와 위험 검토

사용자는 모든 전략의 파라미터와 코드 구조를 직접 결정할 필요가 없다.

# 최종 아키텍처 원칙

QUANT LAB은 처음부터 완성된 거대 금융 플랫폼으로 개발하지 않는다.

정확하게 작동하는 작은 연구 엔진을 구축한 뒤, 그 위에 AI의 자율 연구 능력을 단계적으로 추가한다.

AI는 전략을 자유롭게 연구한다.

백테스트 엔진은 시장의 거래 규칙을 정확하게 재현한다.

검증 엔진은 사전에 고정한 기준으로 전략을 평가한다.

연구 저장소는 성공과 실패를 모두 보존한다.

사용자는 실제 자본 집행과 최상위 운영 권한을 가진다.

최종 설계 목표는 기능이 많은 프로그램이 아니라, 신뢰할 수 있는 전략 연구를 반복적으로 수행하는 시스템이다.
