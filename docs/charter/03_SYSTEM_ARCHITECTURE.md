# 제1장. 시스템의 목적

### 1.1 최종 목표

QUANT LAB은 실전 수익 가능성이 있는 퀀트 전략을 발굴·검증하기 위한 **로컬 데스크톱 연구 앱**이다.

앱은 다음 기능을 Claude와 무관하게 독립적으로 수행한다.

1. 시장 데이터 수집·품질 검증·보관
2. 전략 등록과 버전 관리(가설 등록 포함)
3. 재현 가능한 백테스팅
4. 파라미터 탐색과 대량 전략 실험
5. 독립적인 통계·위험 검증과 PASS / HOLD / FAIL / INVALID 판정
6. 전략 비교, 결과 저장, 시각화, 연구 보고서 생성

Claude는 앱 외부에서 다음 역할만 수행한다.

* 전략 아이디어와 연구 가설 제안
* 표준 전략 명세서와 전략 코드 작성
* 앱 자체의 개발·테스트·오류 수정
* 사용자가 내보낸 결과 패킷에 대한 고급 연구 분석과 후속 연구 제안

연구 전략의 개수나 소프트웨어 기능의 규모는 최종 성과지표가 아니다. 최우선 목표는 실제 시장에서 지속 가능한 투자 우위를 발견할 가능성을 높이는 것이며, 앱은 그 수단이다.

### 1.2 독립 작동 요구사항 (필수)

다음 요구사항은 앱의 모든 버전에 적용하며 자동 테스트로 확인한다.

* **R1. AI 비의존**: Claude API, Claude Projects, 그 밖의 어떤 AI 서비스에 연결하지 않아도 1.1의 모든 기능이 완전히 작동한다.
* **R2. AI 호출 0회**: 앱 코드와 의존성에 AI API 클라이언트를 포함하지 않는다. 백테스트, 파라미터 탐색, 검증, 보고서 생성 중 AI 사용량이 발생하지 않는다.
* **R3. 외부 통신 최소화**: 앱이 여는 네트워크 연결은 사용자가 설정한 시장 데이터 공급자뿐이다. 데이터 수집 이후의 모든 작업은 오프라인에서 작동한다.
* **R4. 로컬 소유**: 데이터, 전략, 실험 기록, 판정 설정, 보고서는 사용자 PC의 작업 폴더에 저장된다. 앱은 이 자료를 외부로 자동 전송하지 않는다.
* **R5. 파일 기반 연동**: Claude와의 연동은 사용자가 직접 옮기는 파일(전략 명세서 가져오기, 결과 패킷 내보내기)로만 이루어진다.

R1~R3 검증 방법은 8.1의 독립성 테스트에 정의한다.

### 1.3 설계 철학

* 모듈형 모놀리식 데스크톱 앱 하나로 구현한다. 서버, 계정, 클라우드 동기화를 두지 않는다.
* 연구 엔진(라이브러리)과 화면(GUI)을 분리한다. 엔진은 GUI 없이도 실행·테스트 가능해야 한다.
* 정확성, 재현성, 데이터 품질을 개발 속도보다 우선한다.
* 전략을 만드는 쪽(Claude·사용자)과 전략을 판정하는 쪽(앱의 검증 엔진)의 책임을 분리한다.
* 정식 평가 기준은 실험 결과를 확인하기 전에 고정한다.
* 외부 유료 서비스와 실거래 기능은 기본적으로 비활성화한다.
* 기능 확장은 측정 가능한 필요가 발생했을 때 수행한다.

# 제2장. 기술 스택

### 2.1 기본 개발 환경

대상 운영체제

* 1차: Windows 10/11 x64 (사용자 PC 기준). 소스 실행은 macOS·Linux에서도 가능하도록 유지하되 배포 패키지는 Windows만 만든다.

언어

* Python 3.12

연구 엔진 (기존 구현 유지)

* NumPy, Pandas, Parquet·PyArrow, SciPy, Statsmodels
* 백테스트 엔진은 직접 구현하고 독립 참조 구현과의 교차검증을 통과해야 채택한다(v1.0.0 원칙 유지, 기존 구현이 이를 충족).

데스크톱 화면

* PySide6 (Qt for Python, LGPL)
* 차트: Matplotlib (Qt 백엔드). 화면 차트와 보고서 이미지를 같은 코드로 그린다.

실험 기록

* SQLite (메타데이터·판정·이력, 주요 테이블은 append-only)
* Parquet (가격·시계열 결과), JSON (설정·결과 요약), YAML (판정 설정·전략 명세서)

작업 실행

* 앱 내부 작업 대기열 + 별도 작업 프로세스(Python multiprocessing). 장시간 작업 중에도 화면이 멈추지 않고, 작업은 취소·재개 가능하다.

배포

* PyInstaller로 Windows 실행 파일 묶음(설치 없이 압축 해제 후 실행 가능한 폴더형) 생성
* Python 설치 없이 실행 가능해야 한다.
* 빌드는 GitHub Actions의 Windows 실행 환경 또는 사용자 PC에서 수행한다.

테스트·개발

* pytest, hypothesis, pytest-qt(화면 기본 동작), Git, uv

인증정보

* 데이터 공급자 API 키는 Windows 자격 증명 관리자(keyring)에 저장한다. 파일·로그·DB·결과 패킷에 기록하지 않는다.

### 2.2 기술 선택 원칙과 선택 근거

* PySide6 선택 이유: 기존 Python 엔진을 그대로 쓰는 단일 언어 데스크톱 앱이 가능하고, 웹 서버·JavaScript 프런트엔드·Electron 런타임이 필요 없다.
* 배제한 대안: Electron·Tauri(별도 프런트엔드 스택과 프로세스 간 통신 추가), Streamlit·Dash(로컬 웹 서버 기반으로 데스크톱 앱 요구사항에 비해 상태 관리와 배포가 불리), 웹 서비스 형태(R4 위반 소지).
* Claude는 호환성, 유지보수성 또는 실제 개발상의 이점이 입증되면 대체 기술을 제안하고 채택할 수 있다. 변경 이유와 영향은 `docs/DECISIONS.md`에 기록한다.
* 불필요한 마이크로서비스, 분산 데이터베이스, 메시지 브로커, 웹 서버, 복잡한 프런트엔드 프레임워크는 도입하지 않는다.

# 제3장. 논리적 시스템 구조

### 3.1 전체 구조

```
┌──────────────────────────────────────────────────────────────┐
│  Claude — 전략 연구 및 개발 보조 (앱 외부, 선택 사항)          │
│  전략 아이디어 제안 · 전략 규칙 작성 · 코드 개선 · 결과 분석     │
└──────────────────────────────────────────────────────────────┘
        │ 표준 전략 명세서(.qls.yaml + 선택적 .py)   ▲ 결과 패킷(.zip)
        ▼  사용자가 가져오기                           │ 사용자가 내보내기
┌──────────────────────────────────────────────────────────────┐
│  QUANT LAB — 독립 실행 앱 (사용자 PC, Claude 연결 없이 작동)    │
│                                                              │
│   A. 전략 관리          B. 시장 데이터 관리                    │
│   C. 백테스팅 엔진       D. 독립 검증 엔진                      │
│   E. 대량 전략 실험      F. 결과 분석                          │
│                                                              │
│   G. 연구 저장소 (모든 모듈이 공유하는 append-only 기록)        │
└──────────────────────────────────────────────────────────────┘
        │
        ▼
  전략 결과 및 연구 보고서
  수익률 · MDD · 샤프지수 · 통계 검증 · 채택/탈락
```

v1.0.0의 RESEARCH ORCHESTRATOR는 앱 내부에서 제거한다. 가설 생성과 후속 연구 판단은 앱 외부(Claude 또는 사용자)가 맡고, 앱은 등록·실행·판정·기록만 수행한다. 앱 안에서 AI가 다음 실험을 결정하는 기능은 두지 않는다.

### 3.2 계층 구조

```
quantlab.app   (GUI: 화면, 작업 대기열 표시)      ─┐
quantlab.cli   (명령행: 테스트·자동화·개발용)      ─┼→ quantlab.services (사용 사례 단위 API)
                                                  │        ↓
                                                  └→ 엔진 모듈 A~G (GUI 의존성 없음)
```

* GUI와 CLI는 같은 `services` 계층만 호출한다. 검증·판정 로직을 화면 코드에 두지 않는다.
* 엔진 모듈은 PySide6를 import하지 않는다. 이 규칙은 테스트로 확인한다.

기존 구현과의 대응:

| 모듈 | 기존 `src/quantlab` | v2.0.0에서 추가할 것 |
|---|---|---|
| A. 전략 관리 | `strategies/` (Strategy·MarketView, 기준 전략) | 명세서 가져오기·정적 검사·계보 |
| B. 시장 데이터 관리 | `core/market_data.py` (시장 데이터 구조), `data/`는 아직 비어 있음 | 공급자 어댑터, 품질 검사, 데이터셋 버전, CSV 가져오기, keyring |
| C. 백테스팅 엔진 | `backtesting/` (체결·비용·회계·참조 구현) | 없음(작업 프로세스 실행 포장만) |
| D. 독립 검증 엔진 | `validation/` (분할·지표·Gate·판정) | 최종 평가 확인 단계, 계보 기반 독립성 판단 |
| E. 대량 전략 실험 | 없음 | 탐색 실행기, 시행 등록, 병렬·취소·재개 |
| F. 결과 분석 | 지표 계산 일부 | 차트, 비교, 보고서, 결과 패킷 |
| G. 연구 저장소 | `registry/` (append-only SQLite) | 시행·계보·내보내기 기록 테이블 |
| 공통 | — | `services/`, `cli.py`, `app/` |

### 3.3 기능 모듈

#### A. 전략 관리 (Strategy Manager) — v1 STRATEGY ENGINE 확장

주요 책임:

* 표준 전략 명세서 가져오기와 형식 검사(제4장)
* 연구 가설 등록(프로토콜 제3조 필수 항목)
* 전략 ID·버전·내용 해시 관리
* 전략 상태 기록(IDEA → RESEARCH → VALIDATION → REJECTED / HOLD …, 헌장 제14조)과 변경 근거
* 전략 간 계보(어느 전략에서 파생되었는지, 보류 데이터 결과를 본 뒤 파생되었는지) 기록
* 공통 실행 인터페이스 `Strategy.on_bar(view) -> target_weights` 제공

전략 코드는 시각 t까지의 데이터만 노출하는 읽기 전용 `view`만 받는다. 주문·체결·지표·판정·저장소에 접근할 수 없다.

#### B. 시장 데이터 관리 (Data Manager) — v1 DATA ENGINE

주요 책임:

* 데이터 공급자 연결(초기 1곳), API 키는 keyring 보관
* 가격·거래량·배당·분할 수집과 원본 보존(수정 없이 Parquet + sha256)
* 품질 검사: 거래일 대조, 결측·중복·이상치, OHLC 정합, 기업행동 정합, 공급자 소급 수정 감지
* 데이터셋 버전(원본 해시들의 해시) 부여
* 화면: 보유 데이터 목록, 수집·갱신 버튼, 품질 검사 결과

수집은 사용자 PC에서 실행되므로 클라우드 작업 환경의 네트워크 제한과 무관하다. 사용자가 CSV 파일을 직접 가져오는 경로도 제공하되, 출처를 기록하고 같은 품질 검사를 적용한다.

#### C. 백테스팅 엔진 (Backtest Engine) — v1과 동일

주요 책임: 시간 순서 처리, 신호 → 주문 → 체결 시뮬레이션, 거래비용, 현금·포지션 회계, 거래 원장과 성과 시계열 생성.

전략의 수익성을 높이기 위한 임의의 체결 가정을 적용하지 않는다. 신호는 다음 거래 가능 시점에 체결한다(프로토콜 제8조).

#### D. 독립 검증 엔진 (Validation Engine) — v1과 동일, 보류 데이터 통제 강화

주요 책임:

* 판정 설정(YAML) 등록 시 해시 고정. 수정하면 새 버전
* 시계열 분할(TRAIN / VALIDATION / FINAL HOLDOUT) 적용
* Gate 1~4 자동 판정, Gate 5(모의운용)는 MVP 범위 밖
* 누출 탐지, 회계 불변식 런타임 검사
* 다중검정 보정(DSR 등)에 쓰는 시행 횟수를 E 모듈 기록에서 자동 집계
* PASS / HOLD / FAIL / INVALID 판정과 사유 기록

보류 데이터 통제:

* HOLDOUT 구간 평가는 검증 엔진만 수행하며 화면에 "최종 평가 실행" 단계로 분리한다. 실행 전 확인 창에 "이 전략 계열의 보류 데이터 평가는 1회이며, 결과를 본 뒤 수정한 전략은 이 구간으로 독립 검증할 수 없다"를 표시한다.
* 모든 HOLDOUT 접근은 접근 원장에 기록하며, 같은 전략 계열의 두 번째 접근 결과는 자동으로 "독립성 손상"으로 표시되어 PASS가 불가능하다.
* 이 통제는 Claude뿐 아니라 사용자 조작에도 동일하게 적용된다.

#### E. 대량 전략 실험 (Batch Experiments) — 신규

주요 책임:

* 파라미터 격자·무작위 탐색, 여러 전략·여러 종목의 일괄 백테스트
* 로컬 작업 프로세스에서 병렬 실행(코어 수 한도 설정), 진행률·취소·재개
* 모든 시행을 저장소에 기록(성공·실패·중단 포함). 기록되지 않은 시행이 생기지 않도록 시행 등록 후 실행한다.

제약:

* 탐색은 TRAIN(필요 시 VALIDATION) 구간에서만 수행한다. HOLDOUT 구간 데이터는 이 모듈에 제공되지 않는다.
* 탐색 결과 화면에 시행 횟수와 다중검정 보정 후 지표를 항상 함께 표시한다(헌장 제17조, 프로토콜 제15·16조).
* 앱은 최고 성과 조합을 자동으로 "채택"하지 않는다. 후보 확정은 사용자가 하며, 확정 시점에 파라미터와 판정 설정이 고정된다.

#### F. 결과 분석 (Result Analysis) — 신규(시각화·비교·보고)

주요 책임:

* 성과·위험 지표 계산과 표시(프로토콜 제18조 다섯 영역)
* 차트: 누적 수익, 낙폭(drawdown), 월별 수익률, 파라미터 민감도 열지도, 비용 민감도
* 전략 간·벤치마크 대비 비교 표
* 연구 보고서 생성(프로토콜 제28조 14개 항목, HTML + Markdown, 차트 이미지 포함)
* Claude 분석용 결과 패킷 내보내기(제4장 4.4)

화면은 연구 결과를 정확히 읽게 하는 것이 목적이다. 지표 개수나 장식은 성과가 아니다(헌장 제23조, 제25조).

#### G. 연구 저장소 (Research Registry) — v1 RESEARCH REGISTRY

주요 책임: 가설, 전략·데이터·설정 버전, 실험 설정과 결과, 판정, 실패 원인, 상태 변경, 보류 데이터 접근 원장, 탐색 시행 기록 저장.

* 실험·판정·접근 원장 테이블은 UPDATE/DELETE를 DB 트리거로 차단한다.
* 잘못된 실험은 삭제하지 않고 INVALID 판정과 수정된 새 실험을 연결한다.
* 화면에 "삭제" 기능을 두지 않는다. 숨김(보관) 표시만 허용하며 원본 기록은 남는다.

# 제4장. Claude 연동 인터페이스 — 표준 전략 명세서와 결과 패킷

### 4.1 원칙

* Claude가 만든 전략은 파일로만 앱에 들어온다. 앱은 Claude를 호출하지 않는다.
* 앱에 들어온 전략은 사람이 쓴 전략과 똑같은 검사·검증·기록 절차를 거친다. 출처가 Claude라는 이유로 검증을 생략하거나 완화하지 않는다.
* 명세서 형식은 버전 관리한다(`spec_version`). 형식을 바꾸면 이전 형식 가져오기를 유지하거나 변환기를 제공한다.

### 4.2 표준 전략 명세서 (`*.qls.yaml`, QUANT LAB Strategy Spec v1)

필수 항목(프로토콜 제3조 사전 등록 항목과 일치):

```yaml
spec_version: 1
strategy:
  id: TT-SPY-SMA            # 전략 계열 ID
  version: 1.0.0
  name: SPY 10개월 이동평균 추세 필터
  type: trend_timing        # 헌장 제4조 전략 유형
  author: claude            # claude | user | 기타
  parent: null              # 파생 원본 전략 ID@버전
  derived_after_holdout_view: false
hypothesis:
  class: theory             # theory | data_mining (프로토콜 제4조)
  economic_rationale: ...
  expected_risks: [...]
  falsification: ...        # 반증 조건
universe:
  market: US_ETF
  symbols: [SPY, BIL]
  frequency: daily
rules:
  kind: declarative         # declarative | python
  # declarative: 앱이 제공하는 지표·조건·비중 구성요소만 사용
  signal: { indicator: sma, source: SPY.close, lookback_months: 10, when: month_end }
  long: { SPY: 1.0 }
  else: { BIL: 1.0 }
  # python: entry: strategy.py:MyStrategy (같은 폴더의 코드 파일)
execution:
  signal_time: close
  fill: next_open
  rebalance: monthly
parameters:
  lookback_months: { default: 10, search: [6, 8, 10, 12, 14] }
benchmark: SPY_buy_and_hold
costs: { one_way_bps: 5 }
validation:
  policy: trend_timing_v1   # 앱에 등록된 판정 설정 이름 또는 함께 제출한 정책 파일
```

두 가지 규칙 형식을 지원한다.

* **선언형(declarative)**: 앱에 내장된 구성요소(이동평균, 수익률·모멘텀, 변동성, 순위, 임계값 조건, 비중 규칙 등)만 조합한다. 코드 실행이 없으므로 기본 형식으로 권장한다. 구성요소는 필요가 확인될 때만 추가한다.
* **Python 코드형(python)**: 선언형으로 표현할 수 없는 전략은 기존 `Strategy` 인터페이스를 구현한 `.py` 파일을 함께 가져온다.

### 4.3 가져오기 절차

```
파일 선택 → 형식 검사(스키마) → 코드 정적 검사(코드형만)
→ 내용 해시 계산·전략 등록(상태 IDEA) → 합성 데이터 스모크 테스트
→ 누출 검사(미래 구간을 변형해도 과거 신호가 바뀌지 않아야 함)
→ 통과 시 상태 RESEARCH, 실패 시 사유와 함께 IDEA 유지
```

코드형 전략에 대한 안전장치:

* import 허용 목록(numpy, pandas, math, statistics 등)만 허용. 파일·네트워크·프로세스·동적 실행(os, sys, subprocess, socket, open, eval, exec, importlib 등) 사용 시 가져오기 거부
* 전략 코드는 별도 작업 프로세스에서 시간 제한을 두고 실행하며, `view` 외의 앱 내부 객체를 전달하지 않는다.
* 이 장치는 실수와 누출을 막는 장치이며 악성 코드에 대한 완전한 보안 경계가 아니다. 신뢰하지 않는 출처의 코드형 전략은 가져오지 않는다. 앱은 가져오기 전에 코드 전문을 화면에 보여준다.

### 4.4 결과 패킷 (Claude 분석용 내보내기)

사용자가 선택한 실험·전략에 대해 다음을 하나의 ZIP으로 내보낸다.

* 연구 보고서(Markdown), 지표 JSON, 일별 성과 시계열, 거래 원장
* 사용한 명세서, 판정 설정, 데이터셋 버전, 앱 버전, 탐색 시행 기록 요약
* 제외: API 키, 원본 시장 데이터 전체(필요 시 사용자가 별도 선택)

HOLDOUT 결과가 포함된 패킷을 내보내면 앱은 해당 전략 계열에 "보류 데이터 결과 외부 공유됨"을 기록한다. 이 패킷을 근거로 Claude가 제안한 수정 전략은 `derived_after_holdout_view: true`로 가져와야 하며, 앱은 계보를 확인해 기존 HOLDOUT 구간을 독립 검증으로 인정하지 않는다(헌장 제11조, 프로토콜 제12조). 독립 검증은 새로 축적되는 데이터(전진 HOLDOUT)로 수행한다.

# 제5장. 모듈 간 데이터 흐름

### 5.1 연구 실행 흐름

```
(앱 외부) Claude 또는 사용자: 아이디어 → 표준 전략 명세서 작성
        ↓ 가져오기
A. 전략 관리: 형식·누출 검사, 가설 등록
        ↓
B. 시장 데이터 관리: 데이터셋 버전 선택·품질 확인
        ↓
C. 백테스팅 / E. 대량 전략 실험: TRAIN·VALIDATION 탐색
        ↓ 사용자가 후보 확정 → 파라미터·판정 설정 고정
D. 독립 검증 엔진: Gate 1~4, HOLDOUT 1회 평가, 판정
        ↓
G. 연구 저장소: 모든 단계 기록
        ↓
F. 결과 분석: 비교·시각화·보고서 → (선택) 결과 패킷 내보내기 → Claude 분석
```

모든 실험은 고유 ID와 버전을 가진다.

### 5.2 검증 독립성

v1.0.0에서 연구 AI와 검증 엔진이 같은 환경에 있던 구조를, v2.0.0에서는 다음으로 대체한다.

* Claude는 사용자 PC의 앱 작업 폴더(데이터, 저장소, 판정 설정, HOLDOUT)에 접근하지 않는다. Claude가 보는 것은 사용자가 내보낸 결과 패킷뿐이다.
* 따라서 전략을 만드는 쪽과 판정하는 쪽이 실행 환경 수준에서 분리된다. 이는 04 문서 Phase 4가 요구한 "AI의 코드 수정 권한과 최종 검증 데이터 접근 권한 분리"를 충족하는 기본 구조다.
* 남는 위험은 앱 코드 자체다. 앱 코드는 Claude가 개발하므로, 검증 로직 변경은 (1) 저장소 커밋으로 추적하고, (2) 통제 실험 테스트(8.1)를 통과해야 배포하며, (3) 실험 기록에 앱 버전과 코드 해시를 남긴다. 검증 기준을 완화하는 코드 변경은 사용자 승인 대상이다.
* 사용자도 보류 데이터를 반복 열람해서는 안 되며, 앱은 3.3 D의 원장으로 이를 기록·차단한다.

다음 요소는 일반적인 전략 실행 과정에서 수정할 수 없다: 확정된 판정 설정, 원본 실험 결과, 원본 데이터 버전 식별자, 보류 데이터 접근 원장, 검증 엔진의 필수 통과 조건, 실거래 권한 정책(기능 자체가 없음).

# 제6장. 앱 화면 구성 (MVP)

화면은 첨부 다이어그램의 여섯 기능에 맞춰 다음으로 한정한다.

1. **데이터**: 데이터셋 목록, 공급자 키 설정, 수집·갱신, CSV 가져오기, 품질 검사 결과
2. **전략**: 전략 목록·상태·버전 계보, 명세서 가져오기, 코드 보기, 가설 내용
3. **실험**: 단일 백테스트 실행, 파라미터 탐색 설정·실행, 작업 대기열(진행률·취소)
4. **검증**: 판정 설정 보기·등록, 후보 확정, 최종 평가 실행, Gate별 결과와 판정 사유
5. **결과**: 차트, 지표 표, 전략 비교, 보고서 생성, 결과 패킷 내보내기
6. **기록**: 실험 이력, 시행 횟수, HOLDOUT 접근 원장, 상태 변경 이력(읽기 전용)

앱 첫 실행 시 작업 폴더를 지정한다(기본값 `문서\QuantLab`). 백업은 이 폴더를 복사하는 것으로 충분해야 한다.

# 제7장. 데이터 및 실험 관리

### 7.1 작업 폴더 구조 (사용자 PC)

```
QuantLab\                 # 사용자 작업 폴더 (앱 설치 폴더와 분리)
├── registry.sqlite       # 연구 저장소
├── data\raw\  data\processed\
├── strategies\           # 가져온 명세서·코드 사본(해시 이름)
├── policies\             # 등록된 판정 설정(해시 고정)
├── artifacts\            # 실험별 시계열·거래 원장(Parquet/JSON)
├── reports\              # 보고서
└── exports\              # 결과 패킷
```

개발 저장소(`quant-lab`)는 앱 소스 코드만 담고, 사용자의 연구 데이터와 기록은 이 작업 폴더에만 둔다.

### 7.2 실험 기록 필드

각 실험은 다음 정보를 저장한다.

* experiment_id
* strategy_id, strategy_version, strategy_hash
* spec_version, strategy_origin (claude / user)
* dataset_version
* configuration_version
* validation_policy_version
* app_version, app_code_hash (v1의 code_commit 대체: 배포 빌드의 Git 커밋과 빌드 해시)
* random_seed
* execution_timestamp
* batch_id, trial_index (대량 실험 소속 시)
* metrics
* verdict
* failure_reason

정식 검증 결과는 동일한 실험 ID로 덮어쓰지 않는다.

### 7.3 데이터 관리와 데이터베이스

원본 데이터는 수정 없이 보존하고, 정제 데이터는 원본 식별자·처리 코드 버전·처리 설정과 연결한다. SQLite 하나와 Parquet 파일로 운영하며, 병목이 실제로 확인되기 전까지 별도 DB 서버를 도입하지 않는다.

# 제8장. 시스템 정확성 테스트

### 8.1 필수 테스트

v1.0.0의 회계·시점·거래·검증·재현성 테스트를 모두 유지하고 다음을 추가한다.

독립성 테스트 (1.2 R1~R3)

* 의존성 목록과 소스에 AI API 클라이언트(anthropic 등)가 없음을 확인
* 네트워크를 차단한 상태에서 데이터 수집 외 전 기능(가져오기 → 탐색 → 검증 → 보고서)이 통과하는 통합 테스트
* 앱이 설정된 데이터 공급자 외의 주소로 연결을 시도하지 않음을 확인

전략 가져오기 테스트

* 형식 오류·필수 항목 누락 명세서 거부
* 금지 import를 쓰는 코드형 전략 거부
* 미래 데이터를 읽는 전략이 누출 검사에서 걸림
* 같은 내용은 같은 해시, 한 글자 변경은 새 버전

대량 실험 테스트

* 모든 시행이 저장소에 기록되고 시행 횟수가 DSR 계산에 반영됨
* 탐색 모듈이 HOLDOUT 구간 데이터를 받지 못함
* 작업 취소 후 재개 시 중복·누락 시행이 없음

화면·배포 테스트

* 엔진 모듈이 GUI 라이브러리를 import하지 않음
* 주요 화면 흐름의 기본 동작(pytest-qt)
* 깨끗한 Windows 환경(Python 미설치)에서 배포 패키지 실행 확인

### 8.2 테스트 통과 원칙

핵심 회계·시간 순서·검증 테스트가 실패한 빌드는 배포하지 않는다. 시스템 정확성이 증명되지 않은 빌드로 얻은 결과는 정식 검증 결과로 인정하지 않는다.

# 제9장. 초기 개발 범위

### 9.1 최소 실행 버전 — MVP (최종 산출물: 실제로 사용 가능한 데스크톱 앱)

MVP 필수 조건:

1. Windows에서 설치(압축 해제) 후 바로 실행되는 데스크톱 앱
2. 하나의 자산군, 하나의 데이터 공급자(+ CSV 가져오기)
3. 표준 전략 명세서 v1 가져오기(선언형 + 코드형)
4. 하나의 기준 전략과 벤치마크
5. 기본 백테스팅과 현실적인 기본 거래비용
6. 파라미터 탐색(TRAIN 구간) 및 시행 기록
7. 시계열 표본 외 검증과 Gate 1~3 자동 판정(Gate 4 일부)
8. 필수 성과·위험지표, 차트, 전략 비교
9. 실험 결과 저장·재현, 보고서와 결과 패킷 내보내기
10. 핵심 단위·통합·독립성 테스트

MVP 범위 밖: 실거래·모의운용(Gate 5), 다중 사용자, 클라우드 동기화, 자동 업데이트, 앱 내 AI 기능, 플러그인 시스템, 복수 자산군 동시 지원, macOS 배포 패키지.

### 9.2 MVP 성공 기준

다음 조건을 사용자 PC에서 실제로 확인하면 MVP를 완료한 것으로 본다. 수익성 있는 전략 발견은 성공 조건이 아니다.

* 사용자가 앱만으로(Claude 연결 없이) 데이터 수집 → 전략 가져오기 → 백테스트 → 탐색 → 검증 → 판정 → 보고서까지 수행할 수 있다.
* 거래비용과 회계 계산이 정확하다.
* 데이터 누출을 방지한다.
* 독립 검증을 실행하고, 실패 전략을 올바르게 탈락시킨다.
* 동일 실험을 재현할 수 있다.
* 탐색·검증 과정에서 AI 사용량이 0이다.
* Claude가 작성한 명세서를 가져와 같은 절차로 검증할 수 있다.

# 제10장. 확장 정책

### 10.1 확장 우선순위

MVP 이후 기본 순서:

1차 — 연구 품질: 데이터 품질 개선, 2차 공급자 교차검증, 검증 방법 보강, 선언형 구성요소 보강
2차 — 연구 범위: 추가 시장·자산군·전략 계열
3차 — 운영: 모의운용(Gate 5)용 일일 갱신·신호 기록, 실행 시간 최적화
4차 — 편의: 화면 개선, 보고서 형식 확대

이 순서는 실제 병목과 필요에 따라 조정할 수 있다. v1.0.0의 "AI 연구 자동화" 단계는 앱 내부 기능으로 두지 않는다. Claude의 연구 생산성 향상은 명세서 형식과 결과 패킷 품질 개선으로 다룬다.

### 10.2 과도한 개발 방지

검증된 필요가 없으면 구현하지 않는다: 앱 내 AI 연동, 멀티에이전트, 클라우드·분산 실행, 웹 서비스, 실시간 데이터 파이프라인, 고빈도 매매 인프라, 실거래 주문 시스템, 불필요한 머신러닝 모델, 모든 자산군 동시 지원, 장식적 대시보드.

새 기능은 해결할 문제, 기대 효과, 유지 비용, 검증 방법을 먼저 기록한다(헌장 제25조).

# 제11장. 개발 주도권과 역할

### 11.1 Claude의 역할

Claude는 앱의 세부 설계와 개발을 주도한다: 작업 분해, 구현 순서, 코드 작성과 테스트, 의존성 관리, 오류 수정, 배포 빌드, 개발 기록.

연구 측면에서 Claude는 앱 외부의 보조 연구자로서 가설과 명세서를 제안하고, 사용자가 제공한 결과 패킷을 분석해 후속 연구를 제안한다. 연구 판단의 자율성(헌장 제6·7조)은 유지하되, 실행과 판정은 앱이 하고 앱 조작은 사용자가 한다.

다음은 사용자 승인이 필요하다: 헌장·프로토콜 수정, 검증 정책의 본질적 완화(검증 코드 변경 포함), 유료 자원 사용, 실거래 권한, 고위험 외부 작업.

### 11.2 사용자 역할

사용자는 연구소의 최종 감독자이자 앱 운영자다: 연구 목표 설정, 예산·인프라 승인, 데이터 공급자 계정 관리, 앱에서의 실험 실행과 후보 확정, 결과 패킷 공유 여부 결정, 실거래 여부 결정.

사용자는 전략의 파라미터와 코드 구조를 직접 정할 필요가 없다.

# 최종 아키텍처 원칙

QUANT LAB은 사용자 PC에서 혼자 작동하는 정확한 연구 앱이다.

Claude는 아이디어와 코드를 제공하지만, 앱은 Claude 없이 데이터를 모으고, 전략을 실행하고, 사전에 고정한 기준으로 판정한다.

백테스트 엔진은 시장의 거래 규칙을 정확하게 재현한다.

검증 엔진은 전략의 출처와 무관하게 같은 기준으로 평가한다.

연구 저장소는 성공과 실패를 모두 보존한다.

사용자는 실제 자본 집행과 최상위 운영 권한을 가진다.

최종 설계 목표는 기능이 많은 프로그램이 아니라, 신뢰할 수 있는 전략 연구를 반복적으로 수행하는 데스크톱 앱이다.
